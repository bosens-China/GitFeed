# 测试与验证

编写测试或检查代码改动时，使用本规范。

## 选择并放置测试

- 测试放在被测业务文件所在模块的 `test/` 子目录，并沿用项目的命名方式。
- 用户指定了测试框架时，使用指定框架。
- 用户没有指定，但项目已经有测试框架时，继续沿用。
- 前两项都没有答案时，默认使用 Vitest。

## 只测试重要行为

- 优先测试业务计算、数据转换、权限判断、请求错误处理、复杂 Hook、关键状态变化，以及容易造成严重回归的工具函数。
- 普通文案、简单布局、纯展示组件、快照和频繁变化的 UI 细节，默认不测试。
- 组件包含关键逻辑时，优先把逻辑拆到 Hook、Composable 或工具函数后测试。只有交互本身关键且容易回归时，才增加组件测试。
- 测试的目的是降低风险。不要为了测试数量或表面覆盖率编写低价值用例。

## 按风险验证改动

- 完成后查看项目已有的类型检查、Lint、测试和构建命令，只运行与本次改动相关的检查。
- 单个低风险文字或字符修改，不需要运行整套检查。
- 修改多个文件、公共模块、业务逻辑、类型或构建配置时，运行对应的 TypeScript、ESLint、测试或构建检查。
- 完成一批相关改动后再统一检查，避免每修改一个文件就重复运行相同的全量命令。
