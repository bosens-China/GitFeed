# 项目与架构

开发前需要确认产品范围、初始化项目或选择技术方案时，使用本规范。

## 确认产品上下文

先从任务和项目中寻找答案。只有信息未知，而且答案会影响实现时，才询问用户。用户已经说明过的内容不要重复询问。

- 新建或大幅调整界面时，先确认目标用户。地区、语言和使用习惯都会影响界面设计。
- 如果尺寸范围不明确，确认需要支持 PC、平板和 H5 中的哪些设备。
- 如果主题范围不明确，确认是否同时支持 Light 和 Dark 模式。
- 第一次处理 React 项目时，检查项目是否启用了 React Compiler。项目中没有答案时询问一次，后续沿用已经确认的选择。启用后按照对应版本的官方写法实现。

## 区分新项目与旧项目

- 新项目直接采用本规范的默认做法。
- 旧项目继续使用已经稳定运行的方案。新增代码优先采用本规范。
- 如果这次本来就要修改某段旧代码，可以顺手让这部分符合新规范。
- 不要为了统一风格继续修改无关文件。用户明确要求整体重构时，再系统替换旧实现。

## 配置开发环境

- Docker Compose、Hono 等服务需要显式配置端口。创建项目时，选择一个当前未占用的冷门端口，例如 `10107`。
- 端口选定后写入项目配置，后续保持不变。不要在每次启动时重新生成端口。
- Vite 会在端口冲突时自动递增，因此不需要单独分配随机端口。
- 默认使用 pnpm。Monorepo 使用 pnpm workspace 管理包。
- 多个构建、测试或发布流程确实需要编排和缓存时，再引入 Turborepo。
- 前端项目尽早配置清晰的路径别名。Node.js 项目优先使用原生的 `imports` 和 `exports`，避免大量深层相对路径。

## 选择架构和依赖

- 项目已经使用 TypeScript 前端时，后端优先考虑 Hono 等 TypeScript 方案。可以使用 Monorepo 复用类型、验证规则和公共代码。
- 同一种语言和 Monorepo 只是默认方向。如果业务、团队或用户指定了其他技术，应当服从实际约束。
- 写代码前，先检查项目中是否已有实现或依赖。没有合适方案时，再查看 GitHub 和社区项目。
- 选择社区方案时，不要只看 Star。还要看需求是否匹配、最近更新时间、维护活跃度、类型支持、许可证、依赖成本和技术栈兼容性。
- 只有社区方案确实比自行实现更合适，而且不会带来不合理成本时，才增加依赖。
